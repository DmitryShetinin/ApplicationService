

# Инструкция по запуску

## Требования

Для запуска приложения необходимо установить:

* Docker
* Docker Compose

Проверить установку:

```bash
docker --version
docker compose version
```

## Запуск приложения

Клонировать репозиторий:

```bash
git clone <repository-url>
cd ApplicationService
```

Собрать и запустить все сервисы:

```bash
docker compose up --build
```

После успешного запуска будут подняты:

* ASP.NET Core Web API
* PostgreSQL база данных
* React клиентское приложение (если используется отдельный frontend контейнер)

API доступен по адресу:

```
http://localhost:5353
```

Swagger доступен:

```
http://localhost:5353/swagger
```

Для полного пересоздания окружения:

```bash
docker compose down -v
docker compose up --build
```

Команда удаляет контейнеры и volume базы данных, после чего приложение выполняет миграции и повторную инициализацию данных.

# Краткое описание реализованного бизнес-процесса

Система представляет собой сервис управления заявками (Ticket Management System).

Основной бизнес-процесс:

1. Пользователь создаёт заявку.
2. Заявке назначается автор.
3. При необходимости назначается исполнитель.
4. Заявка получает начальный статус.
5. Исполнитель обрабатывает заявку и изменяет её состояние.
6. Все изменения фиксируются в истории событий.
7. Пользователь может отслеживать актуальное состояние заявки через Kanban-доску.

Общий жизненный цикл заявки:

```
Создание
   ↓
Новая заявка
   ↓
Назначение исполнителя
   ↓
В работе
   ↓
Завершена
```

Дополнительно реализована возможность:

* перемещения заявок между статусами;
* изменения исполнителя;
* удаления заявок;
* просмотра статистики;
* получения данных для Kanban представления;
* получения уведомлений через SignalR.

# Описание реализованных бизнес-правил

## 1. Правила переходов статусов

Для заявки реализована конечная машина состояний.

Допустимые переходы:

```
New
 ↓
InProgress
 ↓
Completed
```

Недопустимые переходы блокируются на уровне доменной модели.

Например:

```
Completed → New
```

невозможен.

---

## 2. Автор заявки обязателен

При создании заявки система проверяет существование автора.

Если сотрудник не найден:

```
CreateTicket -> Failure
```

Заявка не создаётся.

---

## 3. Исполнитель является необязательным

При создании заявки исполнитель может отсутствовать.

В дальнейшем исполнитель может быть назначен отдельно.

---

## 4. История изменений

Каждое изменение заявки создаёт событие:

* изменение статуса;
* изменение исполнителя;
* изменение основных параметров.

История позволяет восстановить последовательность действий над заявкой.

---

## 5. Контроль конкурентных изменений

Для сущности заявки используется механизм оптимистической блокировки.

В таблице хранится версия:

```
Version
```

При обновлении выполняется проверка актуальности версии.

Если запись была изменена другим пользователем:

```
DbUpdateConcurrencyException
```

обрабатывается приложением.

---

## 6. Уникальность номера заявки

Каждая заявка получает уникальный номер:

```
Ticket.Number
```

Повторное создание заявки с существующим номером невозможно.

# Описание выполненной оптимизации базы данных

## Используемая СУБД

PostgreSQL 17.

---

## Индексация

Для ускорения часто используемых запросов были добавлены индексы.

Основные сценарии:

### Получение заявок по статусу

Запрос:

```sql
WHERE "Status" = ...
```

Индекс:

```sql
CREATE INDEX IX_Tickets_Status
ON "Tickets"("Status");
```

Позволяет быстро получать заявки для Kanban-доски.

---

### Поиск заявок исполнителя

Запрос:

```sql
WHERE "ExecutorId" = ...
```

Индекс:

```sql
CREATE INDEX IX_Tickets_ExecutorId
ON "Tickets"("ExecutorId");
```

---

### Поиск заявок автора

Запрос:

```sql
WHERE "AuthorId" = ...
```

Индекс:

```sql
CREATE INDEX IX_Tickets_AuthorId
ON "Tickets"("AuthorId");
```

---

### Сортировка по дате создания

Основной сценарий:

```sql
ORDER BY "CreatedAt" DESC
```

Индекс:

```sql
CREATE INDEX IX_Tickets_CreatedAt
ON "Tickets"("CreatedAt");
```

SELECT *

## Дополнительные оптимизации

Также были выполнены:

### 1. Ограничение выборки

Используется пагинация:

```sql
LIMIT / OFFSET
```

Вместо загрузки всех заявок сразу.

---

### 2. Projection вместо полного Entity

Используются DTO-запросы:

```csharp
.Select(x => new TicketResponse
{
    Id = x.Id,
    Description = x.Description,
    Status = x.Status
})
```

Что уменьшает количество передаваемых данных.

---

### 3. AsNoTracking

Для read-only запросов:

```csharp
.AsNoTracking()
```

Это уменьшает нагрузку на ChangeTracker EF Core.
